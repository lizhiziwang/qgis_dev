# 影像切片改用 native:tilesxyzdirectory 并添加日志

日期：2026-08-10
分支：dev

## 背景

「影像切片（XYZ）」工具原用 `gdal:gdal2tiles`（按栅格图层直接切，不关心画布）。
用户要求改用 QGIS 原生 `native:tilesxyzdirectory`，并给工具加日志输出
（任务日志框 + 应用日志面板）。

## 关键差异：gdal2tiles → tilesxyzdirectory

| 维度 | gdal:gdal2tiles | native:tilesxyzdirectory |
|---|---|---|
| 输入 | INPUT 栅格图层对象 | **无 INPUT**，按**当前地图画布**渲染 |
| 范围 | 由图层决定 | 由 `EXTENT`（本工具取所选图层范围）+ 图层 CRS 决定 |
| 缩放 | `ZOOM` 字符串 `"min-max"` | `ZOOM_MIN` / `ZOOM_MAX` 两个 int |
| 格式/重采样 | PROFILE / RESAMPLING | TILE_FORMAT(PNG/JPG)、TILE_WIDTH/HEIGHT、ANTIALIAS |
| HTML | VIEWER 枚举 0/4 | 必有 `OUTPUT_HTML` 目标；传空串即不生成 |
| 输出 | 一个 folderDestination | `OUTPUT_DIRECTORY` + `OUTPUT_HTML` 两个目标 |
| 失败 | 命令失败**不抛异常**，仅经 reportError 报 "error code N" | 失败走异常（QgsProcessingException） |

`to_native_params()` 里 EXTENT 传 `"xmin,xmax,ymin,ymax [EPSG:xxx]"` 字符串；
`OUTPUT_HTML` 勾选查看器时写 `output_dir/index.html`，否则传空串。

## 日志捕获要点

- QGIS 3.40 的 `QgsProcessingFeedback` 信号面很窄：只有 `progressChanged` /
  `canceled` / `processedCountChanged`。算法日志走 `push*` **虚方法**回调，
  必须子类化覆写才能拿到（不能 connect）。
- `native:tilesxyzdirectory` 运行时：每级瓦片数经 `pushWarning` 报
  （"N tiles will be created for zoom level M"），结果经 `pushInfo` 报。
- 与进度信号同款线程规则：worker 线程发出的 `log_line` 先投递到主线程
  普通 Python 方法，再更新 QWidget，避免原生崩溃 0xC0000409。
- `reportError` 里的 `"Process returned error code N"` 是 gdal 命令失败的标志；
  native 算法失败走异常分支。两者都转成任务失败（`run()` 返回 False →
  `taskTerminated` → 对话框提示失败）。

## 后续修复：窗口未响应（QgsTask → 普通线程）

切换 native 算法后，执行切片时影像切片窗口一直未响应（进程直接崩掉，退出码
127）。排查过程：

- `_probe_hang.py`（taskManager 路径 + 事件循环）：任务在后台线程完成但进程
  exit 127（崩溃）。
- `_probe_isolate.py`（不连接任何信号，仅提交任务）：依然 exit 127 → 崩溃点在
  `QgsTaskManager` 后台线程 + native 算法本身，与我们的信号接线无关。
- `_probe_thread.py`（同一份 `processing.run("native:tilesxyzdirectory", params)`
  改在普通 `threading.Thread` 里跑，主线程泵事件）：**稳定**——心跳正常、
  6 张瓦片、exit 0。

根因：`native:tilesxyzdirectory` 内部用 `QgsMapRendererParallelJob` 渲染，
经 `QgsTaskManager` 的工作线程运行生命周期不兼容 → 原生崩溃。普通
`threading.Thread` 则完全正常。

修复（普通线程方案）：

| 文件 | 改动 |
|---|---|
| `app/core/domain/imagery_tiles/task.py` | `CreateImageryTileTask` 从 `QgsTask` 改为 `QObject` + `daemon threading.Thread`；`start()` 启动线程，`cancel()` 调 `feedback.cancel()`；信号面保持兼容（`progress_updated` / `log_message` / `taskCompleted` / `taskTerminated` + `exception` / `result_output` / `feedback` 属性） |
| `app/core/domain/imagery_tiles/service.py` | `submit()` 不再提交到 `QgsApplication.taskManager()`，只构造并返回任务对象 |
| `app/ui/dialogs/imagery_tile.py` | `_on_execute` 连接四个信号后调用 `self.task.start()`（先连信号再启动，避免快速任务丢完成事件） |

验证：`_probe_real_path.py` 走真实路径（service.submit → 连信号 → start() →
事件循环）——exit 0、6 张瓦片 + index.html、12 条日志全收到、`taskCompleted`
触发、主线程心跳响应正常。探针文件已清理。

## 后续优化：native 算法提速（METATILESIZE + 瓦片数预警）

用户反馈「影像切片算法处理得好慢」。读了 QGIS 源码
`qgsalgorithmxyztiles.cpp`（release-3_40）确认根因，再用探针量化：

**根因**：`native:tilesxyzdirectory` 不是切影像，而是**逐瓦片重渲染整张地图**。

- `prepareAlgorithm` 把图层树里**所有可见图层** `layer->clone()` 后全部作为
  `QgsMapSettings.layers()`（探针证实：矢量面确实被渲染进了瓦片
  `10/842/386.png`）。
- `startJobs` 对每个 metatile 起一个 `QgsMapRendererSequentialJob`，按
  `context.maximumThreads()` 并发。即：每个瓦片 = 一次完整地图渲染（所有可见
  图层 + 标签 + 样式）。
- 耗时主导因素：**瓦片总数**（范围×缩放级，每级约×4）+ **每瓦片渲染成本**
  （可见图层越多越贵）。

**实测对比**（4096×4096 影像 + 1 矢量面，zoom 0-12，75 瓦片）：

| 方案 | 耗时 |
|---|---|
| native METATILESIZE=4（现状） | 2.73s |
| native METATILESIZE=10 | **0.46s**（约 6 倍提速） |
| gdal:gdal2tiles | 3.83s（反而更慢） |

结论：不用换回 gdal2tiles；METATILESIZE 4→10 把 16 瓦片/批次提高到 100
瓦片/批次，大幅减少渲染任务数，产物瓦片完全一致。

**改动**：

| 文件 | 改动 |
|---|---|
| `app/core/domain/imagery_tiles/service.py` | `to_native_params()` METATILESIZE 4→10；新增 `estimate_tile_count()`（与算法 `getMetatiles` 同一套 lon/lat→tile 公式）与 `TILE_COUNT_WARN_THRESHOLD=2000` |
| `app/ui/dialogs/imagery_tile.py` | 执行前 `_estimate_tiles()`（图层范围→WGS84→估算总数），超过阈值弹 QMessageBox 确认，防止误开超大任务 |

验证：`estimate_tile_count` 对探针影像 0-12 估算 75，与算法实际产出一致；
真实任务链路（submit→start→完成）0.33s、瓦片产出、日志齐全。探针已清理。

另注：算法日志里 "N tiles will be created for zoom level M" 报的是 **metatile**
数（每批次可含 ≤metatileSize² 张瓦片），不是单张瓦片数；本工具的任务日志/预警
用 `estimate_tile_count` 的真实单张瓦片数，量级更直观。
