# 分析工具增加「GDAL 处理节点」—— 通用参数 Dialog + 59 个算法

## Context（为什么改）

用户希望在 `app/ui/docks/analyse_dock.py`（`tools_dock.py` 别名）的工具树
接入 GDAL processing 的所有算法。探针确认 QGIS 4.2 当前注册了 **59 个 `gdal:*`**
算法（栅格转换 / 栅格分析 / 栅格地形 / 矢量分析 / 矢量转换 / 数据库导出 /
元数据查询 / 工具），每个算法的参数形状差异巨大（raster calculator 要写
表达式、gdal2tiles 要选范围和层级、viewshed 要选观察点坐标、warpreproject
要选 CRS）。

如果为每个算法单独写 dialog，代码量 ~2500 行，且 90% 是重复的"下拉选图层 /
数字 / 字符串 / 范围 / CRS"样板。用户通过 AskUserQuestion 选了 **「全部加 +
通用 Dialog」**：59 个节点分到 6 个 GDAL 子组下，全部复用**一个**按算法参数
描述动态生成表单的通用 Dialog。

探针发现 QGIS 自带的 `processing.gui.wrappers` 模块已经为每种参数类型实现
了完整 Qt 控件包装器，且 `qgis.gui.QgsGui.processingGuiRegistry()` 暴露
C++ 端的 `createParameterWidgetWrapper(param, WidgetType.Standard)` API。
这是 QGIS 工具箱自家用的实现，本任务把它们重新装配到仓库对话框里。

## 方案

### 1. `app/core/domain/generic_alg/` — 通用服务门面

`GenericAlgJob`（frozen dataclass：algo_id / params / output_name / output_path）
+ `GenericAlgService.run()`：
- `params` 由 dialog 收集好；service 自动注入 ``OUTPUT`` 字段
- 按 destination 参数类型做差异处理（**关键修正**：探针发现
  `alg.outputDefinitions()` 给的是 ``QgsProcessingOutputRasterLayer``，
  而 `results["OUTPUT"]` 实际上是路径字符串，对应 destination 输入参数
  `QgsProcessingParameterRasterDestination`。需按 **destination 参数类** 判断
  而不是 output 定义类）
  - `RasterDestination` → `QgsRasterLayer(path, name, "gdal")`
  - `VectorDestination` → `QgsVectorLayer(path, name, "ogr")`
  - `FileDestination` / `FolderDestination` → ``dict{RESULT_IS_PATH: True, value: path}``
- 输入图层若传图层对象，先 `copy_with_widened_string_fields` 兜底 GDB 脏数据
- `feedback` 不挂 `progressChanged`（防 0xC0000409 native 崩溃，与 BufferService 同规则）
- 输出图层无效时抛 `RuntimeError(...)`

### 2. `app/ui/dialogs/generic_alg.py` — 通用 Dialog

参照 buffer.py 的 layout（左参数 + 右描述 + 下按钮 / 进度条），参数面板
**动态构建**：
- 构造收 `algo_id` → `QgsApplication.processingRegistry().algorithmById(...)`
- 跳过 hidden flag (0x04) 和 destination 输出参数（统一走底部输出面板）
- Advanced flag (0x02) 折叠到「高级」`QGroupBox`（与 QGIS 工具箱一致）
- 每个参数调 `QgsGui.processingGuiRegistry().createParameterWidgetWrapper(...)`
  造 wrapper，wrapper 内部构造 Qt 控件（MapLayerComboBox / FieldComboBox /
  CrsWidget / ExtentWidget / FileWidget 等）—— **不自己手写参数面板**
- `project.layersAdded` / `project.layersWillBeRemoved` 信号驱动所有 wrapper
  refresh（图层增删后下拉内容自动更新）
- `_on_execute` 推迟到 `QTimer.singleShot(0, ...)` 跑 `processing.run`（防 native 崩溃）
- `_run` 按返回值类型决定 `project.addMapLayer` 或 messagebar 提示路径

### 3. `app/ui/docks/tools_dock.py` — 注册 59 个 GDAL 算法

新增 `_GDAL_ALGORITHMS`（模块级清单），按 6 个分组组织：

- **GDAL 栅格元数据**（3）：assignprojection、extractprojection、dataset_identify
- **GDAL 矢量分析**（11）：dissolve、buffervectors、offsetcurve、onesidebuffer、

## 关键 API 备忘

- **Wrapper 创建**：
  ```python
  wrapper = QgsGui.processingGuiRegistry().createParameterWidgetWrapper(
      param_def, QgsProcessingGui.WidgetType.Standard
  )
  wrapper.setWidgetContext(QgsProcessingParameterWidgetContext(...))
  wrapper.registerProcessingContextGenerator(QgsProcessingContextGenerator 子类)
  widget = wrapper.createWrappedWidget(context)   # QWidget
  label = wrapper.createWrappedLabel()           # QLabel or None
  value = wrapper.parameterValue()               # 默认值
  wrapper.refresh()                              # 工程图层变化时调用
  ```
- **Context 生成器**：`QgsProcessingContextGenerator` 在 `qgis.gui`（不在
  `qgis.core`）；必须继承它实现 `processingContext()` 返回 `QgsProcessingContext`
- **destination 类型判断**：用 ``isinstance(dest_param, RasterDestination)``
  等判断输出参数类型；output 定义类（`OutputRasterLayer` 等）只能告诉你"有输出"
  但 `processing.run` 实际返回值（路径字符串 / 图层对象）由 destination 参数
  类型决定
- **GDAL 特点**：所有 GDAL 算法都把结果写文件（临时或用户指定路径），
  `results["OUTPUT"]` 始终是路径字符串（不会给 memory 图层对象）——
  与 QGIS native 算法（`native:buffer` 等）行为不同

## 风险与限制

- **同步执行**：仍 sync `processing.run`。gdal2tiles / contour_polygon / 复杂
  raster calc 可能阻塞 UI 数分钟级别；后续可加后台执行选项
  （仿 shortest_path 的 `QgsProcessingAlgRunnerTask`），本次先满足"能跑"
- **未知 wrapper 类型**：遇 `QgsProcessingParameterMatrix` 等不常见类型会失败，
  service 层 try/except 兜底成 `None`，dialog 显示空 + 不阻塞
- **`BandWidgetWrapper`**：依赖图层 raster bands；图层未加载时 widget 灰显但
  能构建，符合 QGIS 自家工具箱行为
- **测试需 `Processing.initialize()`**：与服务层测试同坑，
  `tests/core/domain/buffer/test_service.py` 已经踩过相同问题
- **pre-existing 失败**：`tests/core/domain/buffer/test_service.py::test_output_path_writes_gpkg`
  仍然失败（与本任务无关，确认是 base 失败）
